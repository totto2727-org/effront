Server Function の結果と更新後のページは同じレスポンスで届きますが、UI で利用できるタイミングは異なります。
画面更新の順序制御は、データベースへの書き込み順序も決めません。

## 一度の呼び出しで結果と更新後のページを返す {#execution}

Effront は Server Function の実行後に、リクエストされたルートを再レンダーします。
ブラウザーからの呼び出しには関数の結果と更新後のページが返るため、送信ハンドラーから画面更新用のリクエストを追加する必要はありません。
設定編集画面なら、ハンドラーが書き込みを完了し、Page が保存済みの設定を読み込み、戻り値で「設定を保存しました」などの結果を伝えます。

JavaScript の読み込み前にネイティブフォームを送信した場合は、成功時に React のフォーム状態を含む完全な HTML ページが返ります。
この動作には、[Server Function ガイド](/guide/server-functions)のように、Server Function の参照をフォームや `useActionState` に直接渡す必要があります。

## 入力の検証と認可は別の役割 {#input-boundary}

`EFFRONT.ServerFn.make` は、ハンドラーを呼び出す前に入力 Schema で引数をデコードします。
Schema のデコードが確認するのは入力であり、レコードを変更する権限ではありません。
書き込み前の認証と認可は、ハンドラーか、その Server Function に適用した [Middleware](/guide/middleware) で行います。
フォームを表示する Page だけを保護しても不十分です。
レコード ID、hidden フィールド、前回のフォーム state は、いずれも信頼できない入力です。

Server Function のボディには 10 MiB、React のブラウザー呼び出し用の引数デコーダーには配列サイズ 10,000 の上限があります。
大きなファイルには別のアップロード手段が必要です。
通信プロトコル上の拒否と、アプリケーションの認可は異なります。

- `Origin` がない、不正な値である、またはその URL の host が `Host` と一致しない場合は 403 になります。
- React の通信プロトコルとしてデコードできない引数やフォームは 400 になります。
- HTTP の入口で上限を超える `Content-Length` を検出すると 413 になります。Server Function のボディ読み取り中に上限を超えると 400 になります。

## 画面より先に関数の結果が届く {#result-and-refresh}

ブラウザーからの呼び出しの Promise は、関数の結果を受信すると resolve または reject し、その後で Effront が更新後のページを反映します。
そのため、ほかの内容が更新中でも、フォームには「設定を保存しました」と表示されることがあります。
`await` の完了やフォームの送信中状態の終了は、更新後の DOM 要素が存在することを保証しません。
その要素へのフォーカス移動や計測は、対象のコンポーネントがレンダーされるまで待つ必要があります。

想定内の業務上の失敗は、[状態を持つフォームの例](/guide/server-functions#state)のように、`useActionState` 用の state として返せます。
入力 Schema の失敗はハンドラーの実行前に起こり、フォームの state へ自動変換されません。
この失敗も、エラーチャネルに残したハンドラーの失敗も、ブラウザーからの呼び出しを reject します。
React が関数を Action として呼び出した場合、この reject は React のエラー処理へ届きます。

更新後のページは、最初に表示された後もストリームを受信し続けることがあります。
別の画面に置き換わると残りの通信は終了し、クライアントの切断によって未完了のサーバー処理が中断されることもあります。
レスポンスを受信できなくても、完了済みの書き込みがロールバックされたとは限らないため、再試行で書き込みが重複する可能性があります。

## 画面更新の順序と書き込み順序は別 {#concurrency}

ブラウザーからの呼び出しは並行して実行されることがあります。
Effront がレスポンスに同梱されたページを採用するのは、次の 3 条件をすべて満たす場合だけです。

- 最後に開始した呼び出しのレスポンスである。
- 呼び出し元の履歴エントリーを現在も表示している。Navigation API がない場合は、呼び出し時と現在の URL を比較します。
- ページ移動が進行中ではない。

条件を満たさない場合は同梱されたページを破棄し、進行中のページ移動が落ち着いてから現在のルートを更新します。
離れたページからのレスポンスによって、そのページへ表示が戻ることはありません。
画面更新の処理は戻る・進む用のページキャッシュを無効化し、関数の失敗結果を含む正しいレスポンスを受け取った場合も同じ処理を行います。

保存 A の後に保存 B を開始すると、遅れて届いた A のレスポンスに同梱されたページがそのまま表示されることは防げますが、A によるデータベースの変更は防げません。
送信中のボタンを無効にすれば繰り返しの送信を減らせますが、再試行や別のタブからの操作は防げません。
アプリケーションに必要な書き込みの保証は、サーバー側での重複検出、バージョン確認、トランザクションで実現する必要があります。
