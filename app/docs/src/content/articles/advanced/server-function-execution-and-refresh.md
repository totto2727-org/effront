保存操作では、データを書き換えるだけでなく、ページを再読み込みしなくても結果が分かるようにする必要があります。
Effront は Server Function の呼び出しに合わせてページを更新しますが、関数の結果、画面への反映、データベースの書き込み保証はそれぞれ別の役割を持ちます。
この記事では、ハンドラーから何を返すか、UI がそれをいつ利用できるか、繰り返しの送信をどう安全に扱うかを説明します。

## 保存から画面更新までの流れを組み立てる {#execution}

`EFFRONT.ServerFn.make` で定義した Server Function と、その関数が変更するデータを読み込む Page を用意します。
定義とフォームへの接続方法は、[Server Function ガイド](/guide/server-functions)を参照してください。
設定編集画面なら、次のように役割を分けます。

1. ハンドラーで操作の妥当性を確認し、設定の書き込みを完了してから戻り値を返します。
2. 呼び出し後に Effront が Page を再レンダーするとき、Page は保存済みの設定を読み込みます。
3. フォームでは関数の戻り値を使い、確認メッセージなど、その操作に対応する結果を表示します。

この分担により、ブラウザー側でサーバーレンダリングの画面を組み立て直すのではなく、保存済みのデータを更新後の表示に使えます。
Effront は呼び出しの処理に続けて再レンダーするため、送信処理に画面更新用のリクエストを追加する必要はありません。

ブラウザーで React が動作している場合、レスポンスには関数の結果と更新後のページが含まれます。
JavaScript の読み込み前にネイティブフォームを送信した場合は、成功時に React のフォーム状態を含む完全な HTML ページが返ります。
このフォームの動作を保つには、基本ガイドのように Server Function の参照をフォームや `useActionState` に直接渡してください。

## フォームを公開する前に書き込みを保護する {#input-boundary}

`EFFRONT.ServerFn.make` は、ハンドラーを呼び出す前に入力 Schema で引数をデコードします。
これは入力の形式を確認するものであり、呼び出したユーザーが特定のレコードを変更してよいかを判断するものではありません。
書き込む前に [Middleware](/guide/middleware) またはハンドラーでユーザーを認証し、要求された操作の権限を確認してください。
レコードの ID、hidden フィールド、前回のフォーム state は、自分の UI から渡した値でも信頼できない入力として扱います。

操作に合った入力サイズの制限を設け、大きすぎる内容を送信した場合はユーザーが修正できるようにします。
Server Function のボディには 10 MiB、React の引数デコーダーには配列サイズ 10,000 の上限があります。
大きなファイルは通常の Server Function の送信内容に含めず、別のアップロード手段を用意してください。

リクエストが拒否された原因を調べるときは、通信プロトコルの検証とアプリケーションの認可を区別します。

- `Origin` がない場合や、その URL の host が `Host` ヘッダーと一致しない場合は 403 になります。
- React の通信プロトコルとしてデコードできない引数やフォームは 400 になります。
- HTTP 入口で上限を超える `Content-Length` を検出すると 413、Server Function のボディ読み取り中に上限を超えると 400 になります。

これらの検証を通過しても、書き込みの権限が与えられるわけではありません。

## ページ全体の更新を待たずに結果を伝える {#result-and-refresh}

ブラウザーからの呼び出しでは、返された Promise で関数の結果を受け取ります。
Promise はその結果を受信すると resolve または reject し、Effront が更新後のページを反映し終えるまでは待ちません。
たとえば、ページの別の部分がまだ更新内容を受信している間に、フォームに「設定を保存しました」と表示されることがあります。
これは、操作結果の表示とページのレンダリングが分かれているために起こる通常の動作です。

フォームの近くに表示したい想定内の業務上の失敗は、ハンドラーから明示的な state として返し、`useActionState` で表示します。
接続方法は、[状態を持つフォームの例](/guide/server-functions#state)を参照してください。
入力 Schema のデコード失敗はハンドラーの実行前に起こるため、その state に自動変換されることはありません。
デコード失敗や、エラーチャネルに残したハンドラーの失敗は、ブラウザーからの呼び出しを reject し、React のエラー処理へ届きます。

`await` の完了やフォームの送信中状態の終了を、更新後の DOM 要素が存在する証拠として使わないでください。
更新後の画面で要素にフォーカスを移したりサイズを計測したりする場合は、そのコンポーネントがレンダーされたタイミングで行います。
ページは最初の表示更新の後もストリームを受信し続けることがあります。

ストリームを受信している画面が別の画面に置き換わると、Effront は残りの通信を終了します。
サーバー側の処理もリクエストの寿命に従うため、クライアントが切断された後も未完了の処理が続く保証はありません。
また、レスポンスを受信できなかったことは、完了済みの書き込みがロールバックされたことを意味しません。
この不確実性を考慮して再試行を設計してください。

## 繰り返しの保存を安全に扱う {#concurrency}

React の準備が済んだ後の呼び出しは、並行して実行されることがあります。
Effront は古いレスポンスから表示中のページを保護しますが、書き込み自体を順番に実行するわけではありません。
たとえば保存 A の後に保存 B を開始すると、遅れて届いた A のレスポンスに同梱されたページがそのまま表示されることは防げますが、A によるデータベースの変更は防げません。

レスポンスに同梱されたページを採用するのは、最後に開始した呼び出しのレスポンスで、呼び出し元の履歴エントリーを現在も表示しており、ページ移動が進行中でない場合だけです。
Navigation API がない場合は、履歴エントリーの代わりに呼び出し時と現在の URL を比較します。
条件を満たさない場合は同梱されたページを破棄し、進行中のページ移動が落ち着いてから現在のルートを再取得します。
そのため、離れたページからのレスポンスによって元のページが表示されることはありません。

画面更新の処理では、戻る・進む用のページキャッシュを無効化します。
関数の失敗結果を含む正しいレスポンスを受け取った場合も更新処理へ進むため、呼び出しが reject したからといって、画面やキャッシュが変わらないとは限りません。

繰り返しの送信を避けたいフォームでは、送信中は送信ボタンを無効にします。
ただし、再試行や別のタブからの操作ではこの UI 上の制限が効かないため、サーバー側でも書き込みの安全性を守ってください。
二重実行を避ける操作には重複検出、新しいデータを上書きしてはいけない編集にはバージョン確認、複数の書き込みをまとめて成功させる必要がある処理にはトランザクションを使います。
Effront の画面更新の順序制御は、これらのデータベースの保証を提供するものではありません。
