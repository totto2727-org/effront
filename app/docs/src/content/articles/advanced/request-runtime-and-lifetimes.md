1 件のリクエストで使うリソースは、Effront に管理させます。
共有リソースとバックグラウンド処理には、別の所有者を設けてください。

## リソースの所有者を決める {#resource-design}

| リソースの用途                         | 所有者                                            | 解放する時点                                     |
| -------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| 1 件のリクエスト                       | リクエストの Scope                                | ストリーミングする本文の完了、失敗、キャンセル時 |
| 接続プールなど、複数のリクエストで共有 | アプリケーションの Layer 外にあるホスト側の所有者 | 利用するすべてのレスポンスが終了した後           |
| レスポンス終了後も続ける処理           | ホストが対応するバックグラウンド処理              | その処理が終了した時点                           |

共有の接続プールを使う場合は、借りた接続の返却処理をリクエストの Scope に登録します。
プールの破棄はホスト側の所有者に任せてください。
ホストから提供するサービスについては、[外部サービスの所有権の契約](/api-reference/http#capture)を参照してください。

> [!NOTE]
> 独立した Promise を開始しても、リクエストのサービスの生存期間は延びません。
> バックグラウンド処理には、その処理が所有するリソースを用意してください。

## リクエストのリソースをアプリケーションの Layer で取得する {#request-layer}

Effront は、`EFFRONT.make({ routes, layer })` に渡す Layer をリクエストごとに構築します。
リクエスト固有の取得処理は `Layer.effect` に置き、`Effect.acquireRelease` で解放処理を登録します。
サービスの宣言と Layer の登録方法は[サービスの設定例](/guide/effect#service)を参照してください。

> [!WARNING]
> リクエスト固有の可変状態は、取得処理の中で作成してください。
> `Layer.succeed(Service, object)` を再利用すると、同じオブジェクトを複数のリクエストで共有します。

## レスポンス本文の終了までリソースを維持する {#response-lifetime}

<span id="render-scope"></span>

遅れてレンダーされるコンポーネントは、ハンドラーが `Response` を返した後も、リクエストのサービスを利用できます。
登録した解放処理は、ストリーミングする本文の終了時にリクエストの Scope に実行させます。
バッファリング済みのレスポンス、本文のないレスポンス、レスポンス生成の失敗では、本文の消費を待たずに Effront が取得済みのリソースを解放します。

> [!WARNING]
> ハンドラーの呼び出しを囲む `finally` ブロックで、リクエスト所有のリソースを閉じないでください。
> レスポンスの生成だけを `Effect.scoped` で囲んだ場合も、ストリーミングする本文が終了する前にリソースを解放してしまいます。
> 独自の HTTP ホストを使う場合は、[リクエストの Scope とレスポンス本文の契約](/api-reference/http#handler)に従ってください。
