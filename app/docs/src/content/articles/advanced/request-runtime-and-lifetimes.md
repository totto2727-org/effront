遅れてレンダーされる Component が使う接続は、HTTP ハンドラーが Response を返した後も、その Component のレンダーが続く間は開いたままにする必要があります。
リソースの取得と解放をリクエストに結び付けることで、ストリーミング中のレンダーが、すでに閉じたリソースを使う事態を防げます。
このガイドでは、解放処理を登録する場所、アプリケーションからのリソースの使い方、レスポンス処理をカスタマイズするときに守るべき点を説明します。

## レスポンス本文の終了に合わせて解放する {#response-lifetime}

ストリーミングするレスポンスでは、ヘッダーを返すことと本文が完了することは別の出来事です。
Fetch ハンドラーの Promise が Response に解決した後も、Suspense の内容や Flight データの生成が続くことがあります。
その Response は進行中の処理として扱い、リソースを閉じる合図とは考えないでください。

Effront は、アプリケーションの Layer で取得したリソースを、レスポンス本文の処理が続く間保持します。

- 本文の読み取り中は、リクエストのリソースを引き続き利用できます。
- 本文の読み取りが完了、失敗、キャンセルすると、リクエストの Scope が閉じ、登録した解放処理が実行されます。
- 本文がない場合やレスポンスの生成が失敗した場合は、ストリームを待たずに、取得済みのリクエストのリソースを解放します。

解放処理をリクエストに結び付ければ、正常終了と中断を同じ解放処理で扱えます。
アプリケーションのリソースごとに、成功時のコールバックと切断時のハンドラーを別々に用意する必要はありません。

## アプリケーションの Layer に取得と解放を登録する {#request-layer}

リクエスト全体でリソースを使えるようにするには、次の手順で接続します。

1. アプリケーションに必要な操作を Effect のサービスとして公開し、そのサービスを `Application.effront<Services>()` に含めます。
2. Layer でそのサービスを構築し、`Effect.acquireRelease` などの Scope に対応した操作で、リソースの取得と解放を組み合わせます。
3. Layer を `EFFRONT.make({ routes, layer })` に渡し、Effront がリクエストを処理するときに構築できるようにします。

サービスの宣言とアプリケーションへの接続方法は、[サービスの設定例](/guide/effect#service)を参照してください。
リクエスト固有の取得処理は Layer の中に置き、モジュールの読み込み時にリソースを開いて後続のリクエスト用に保持しないようにします。

アプリケーションの Layer は、Node.js、Bun、Cloudflare Workers、Alchemy のいずれでもリクエストごとに構築されます。
`createFetchHandler` で再利用可能なハンドラーを作っても、その Layer がサーバー全体で共有されるシングルトンになるわけではありません。

Workers では、Layer の取得処理から、そのリクエストの `env`、execution context、元の `Request` を参照できます。
サービスの構築にこれらの値が必要な場合は、[Workers のコンテキストアクセサー](/platforms/cloudflare#context)を使います。

## Page や Server Function でリクエストのサービスを使う {#render-scope}

同じリクエストのリソースを呼び出し箇所ごとに取得するのではなく、Page、Layout、Component、Server Function の Effect からサービスを取り出して使います。
Effront は、処理中のリクエストのアプリケーションサービスを提供します。
そのため、遅れて始まるレンダーでも、レスポンスのストリーミング中はサービスを引き続き利用できます。

この処理を Effront のリクエスト処理の中で実行するために、アプリケーションの Routes を通してレンダーしてください。
レンダーを管理する Scope は、そのリクエストに属し、別のリクエストとは共有されません。
レンダーのストリームが中断されると、未完了のレンダー処理も中断されます。
アプリケーションのリクエスト実行環境の外や、必要な Middleware が有効でない場所でレンダーすると、サービスを利用できるコンテキストは得られず、`TypeError` になります。

サービスからブラウザーへ渡す値は、公開すると決めたものだけにしてください。
Workers のバインディングが自動的に Flight や HTML へシリアライズされることはありませんが、JSX、Client Component の props、Server Function の戻り値に含めた値は、クライアントへ送られる可能性があります。

## リソースを早く閉じずにレスポンス処理をカスタマイズする {#resource-design}

Fetch ハンドラーをラップする場合は、ストリーミングとキャンセルを維持したまま本文を返してください。
その後の本文の読み取りでもリソースが必要な場合があるため、ハンドラーが Response を返した直後に実行される `finally` ブロックでリクエストのリソースを閉じないでください。
同様に、独自に native HTTP と接続する場合も、レスポンスの生成だけを `Effect.scoped` で囲むのではなく、本文の完了、失敗、キャンセルまでリクエストの Scope を保持する必要があります。

アプリケーションの Layer の外からホスト所有のサービスを提供する場合は、その所有者が、リクエストで使われる間サービスを利用可能に保つ必要があります。
`makeHttpEffect` はそれらのサービスへの参照を保持しますが、サービスを取得したり寿命を延長したりはしません。
これらは、Effront がリクエストごとに構築するアプリケーションの Layer とは別に管理されます。

レスポンス終了後も続ける処理には、ホストが対応するバックグラウンド処理の仕組みと、その処理が所有するリソースが必要です。
Promise を開始したり、リクエストのサービスを外側の変数へ保存したりしても、リクエストの解放処理後までそのサービスを使い続けられるわけではありません。
