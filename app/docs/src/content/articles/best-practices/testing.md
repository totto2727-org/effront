役立つテストは、変更によって利用者に必要な操作が壊れていないかを教えてくれます。
テストするコンポーネントを列挙するのではなく、「アカウントの所有者が表示名を変更し、保存された名前をプロフィールで確認できる」のように、具体的な結果を出発点にしましょう。
この記事では、ブラウザーでその結果を確かめ、関連するルールを個別に検証し、公開予定のビルドでも同じ操作を確認するという、Effront アプリケーションに使える一般的なテストの進め方を紹介します。

## 一連のユーザー操作を起点にする {#pages}

動かなくなると利用者が困る機能を一つ選び、操作前の状態と期待する結果を書き出します。
プロフィール編集なら、表示名が分かっているテストアカウントを用意し、本番のレコードを変更しないように、独立したテスト用のデータ保存先を使います。
そのうえで、起動したアプリケーションを実ブラウザーで操作します。

1. プロフィールの URL を直接開き、現在の名前を確認します。
2. フォームに別の名前を入力して送信します。
3. 利用者に示される処理結果と、ページに表示された更新後の名前を確認します。
4. ページを再読み込みし、保存した名前が引き続き表示されることを確認します。

最後の手順によって、保存された更新と、ローカルな UI の状態だけが変わった場合を区別できます。
アプリケーション内のリンクやブラウザーの戻る・進むからもプロフィールを開き、URL と表示データが一致することを確認します。
これらの確認は、関数だけのテストでは見落とす、ページ、フォーム、サーバーのつながりを検証します。

## 業務ルールをブラウザーから切り離して検証する {#services}

一連の操作が明確になったら、ブラウザーテストにすべてを盛り込むよりも、多くの入力の組み合わせを個別に確かめたほうがよいルールを洗い出します。
プロフィール編集なら、空の名前を拒否すること、他人のアカウントへの変更を拒否すること、更新に失敗した場合は元の名前を維持することなどが考えられます。
関数が正常に戻ったかだけでなく、それぞれの結果と保存データの状態を確認してください。

共有する業務処理は、Page や Server Function から呼び出せる関数や Effect のサービスに切り出します。
その関数やサービスを直接テストします。
Effront の Server Function 自体は、サーバーグラフ内で通常の関数として呼び出すことはできません。
実際のリクエストと描画の経路も検証できるように、フォーム送信はブラウザーテストに残します。
フォームとの接続に関する契約は [Server Functions](/guide/server-functions) を参照してください。

処理が Effect のサービスに依存する場合は、Layer を通してテスト用の実装を提供し、入力、応答、失敗を再現できるようにします。
依存関係を提供する仕組みは [Effect の Layers ガイド](https://effect.website/docs/requirements-management/layers/)、Effront アプリケーションへの接続方法は[サービスのガイド](/guide/effect)で説明しています。
テスト用の代替実装で確認できるのは、その実装に対する処理の振る舞いであり、実際のデータベースや外部 API との連携が動くかどうかではありません。
実際の接続先との振る舞いが重要な場合は、別途、連携を確認するテストを用意してください。

更新が拒否される場合もブラウザーテストに残し、利用者に意図した案内が表示され、データが変わらないことを確かめます。
利用者は hidden フィールドを含む送信値を変更できるため、認可はサーバー側で行う必要があります。
編集ボタンを隠したり無効にしたりするだけでは、認可のテストにはなりません。

## 公開用ビルドを対象の実行環境で確かめる {#production}

公開前に、選んだホスト向けにビルドしたアプリケーションで、重要な一連の操作をもう一度試します。
ホストの本番用エントリーポイントと実行環境を使い、データや認証情報は本番のものではなくテスト用のものを用意します。
ビルド成果物と起動方法は[プラットフォーム](../platforms.md#build-startup)を参照してください。
開発中や別の実行環境で動く preview で成功しても、対象の環境でホスト固有の API が動くことを確認したことにはなりません。

一連の操作を試す際には、URL を直接開くと必要な HTML、CSS、画像が配信され、JavaScript の読み込み後もページを操作できることを確認します。
存在しないページやアセットの URL では、期待する 404 応答になることを確かめます。
意図しない情報漏えいを確認するには、サーバー側の秘密値に識別しやすい架空の値を使い、ブラウザーへ返される HTML や Flight 応答に含まれないことを検証します。
実際の認証情報をテストの目印に使わないでください。

提供する機能と対応するブラウザーに応じて、操作の条件を追加します。
Server Function に接続したフォームでは、JavaScript を無効にして送信と結果のページを確認します。
Suspense を使う読み込み状態では、読み込みの完了と、完了前に別のページへ移動した場合の両方を確認します。
Navigation API 非対応のブラウザーも対象にする場合は、そこでリンク移動を繰り返し、通常のページ読み込みに切り替わる経路も確かめます。

## 繰り返し実行できるテストにする {#tools}

期待する結果が明確になったら、一連の操作とルールの確認を自動化します。
ブラウザーの操作には [Playwright](https://playwright.dev/docs/intro)、個別の処理のテストには [Vitest](https://vitest.dev/guide/) などのテストランナーを使えます。
Playwright の [webServer 設定](https://playwright.dev/docs/test-webserver)を使うと、テスト実行の一部としてアプリケーションを起動できます。

各テストの初期状態を決め、同時に動くテストが互いのデータを上書きしないようにします。
細かなルールの組み合わせは小さな処理のテストで網羅し、ブラウザーテストは利用者にとって重要な操作や連携の失敗に集中させます。
これらの確認をすり抜けた不具合が見つかったら、その不具合を検出できたはずの箇所に回帰テストを追加し、元のユーザー操作も引き続き成功することを確かめましょう。
